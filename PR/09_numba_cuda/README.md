# Практическое занятие № 5.2: Использование компилятора Numba для генерации кода под GPU

## Описание и цель работы
Работа посвящена исследованию архитектуры параллельных вычислений на графических процессорах (NVIDIA CUDA) с использованием компилятора **Numba**. Рассматриваются принципы запуска вычислительных ядер (Kernels), иерархия сетки потоков (Grids, Blocks, Threads), безопасная адресация элементов без выхода за границы массивов, а также реализация двумерного генератора множества Мандельброта.

Реализация спроектирована как отказоустойчивый модуль: скрипт содержит целевые CUDA-кернелы под графический процессор, дополненные автоматической проверкой доступности среды (`cuda.is_available()`) и резервным многопоточным контуром (CPU-fallback) для запуска на системах без аппаратной поддержки CUDA.

---

## Аппаратный статус среды выполнения

При выполнении первичной диагностики аппаратного обеспечения зафиксированы следующие параметры окружения:
* **Интерпретатор:** Python 3.10+ (64-bit);
* **Статус CUDA:** Аппаратный ускоритель NVIDIA на локальном хосте не инициализирован (`CUDA Device Initialized: False`);
* **Режим работы программы:** Программа автоматически переключилась в режим безопасной эмуляции/CPU-fallback. Алгоритмы CUDA-ядер реализованы в строгом соответствии со спецификацией задания, а сравнительный бенчмарк сопоставляет локальные CPU-замеры с эталонными показателями методического стенда (NVIDIA GeForce MX230).

## Архитектура вычислений CUDA в Numba

```text
               Хост (CPU / Python Runtime)
                            │
              Параметры     │ [blocks_per_grid, threads_per_block]
              запуска ядра  ▼
               Сетка потоков (Grid)
          ┌─────────────────┴─────────────────┐
          ▼                                   ▼
    Блок (0, 0)                         Блок (X, Y)
  ┌───────┴───────┐                   ┌───────┴───────┐
  ▼               ▼                   ▼               ▼
Поток (0, 0)    Поток (15, 15)      Поток (0, 0)    Поток (15, 15)
  │               │                   │               │
  └───────┬───────┘                   └───────┬───────┘
          ▼                                   ▼
   Локальная память                    Локальная память
          │                                   │
          └─────────────────┬─────────────────┘
                            ▼
               Глобальная память GPU (VRAM)
              [Матрица пикселей изображения]
```

### Формулы индексации:
* **Одномерная сетка (1D):**
  $$\text{position} = \text{cuda.blockIdx.x} \times \text{cuda.blockDim.x} + \text{cuda.threadIdx.x}$$
* **Двумерная сетка (2D):**
  $$x = \text{cuda.blockIdx.x} \times \text{cuda.blockDim.x} + \text{cuda.threadIdx.x}$$
  $$y = \text{cuda.blockIdx.y} \times \text{cuda.blockDim.y} + \text{cuda.threadIdx.y}$$

## Результаты работы программы

### 1. Безопасная адресация элементов
При размере массива $N = 1000$ и размере блока в 16 потоков сетка выделяет $\lceil 1000 / 16 \rceil = 63$ блока, что суммарно даёт 1008 потоков. Условие `if position >= my_array.shape[0]: return` гарантирует отсутствие ошибок нарушения границ памяти (`Access Violation`) и защищает память от перезаписи избыточными потоками.

### 2. Генерация фрактала Мандельброта
Для координатной сетки $2000 \times 2000$ пикселей сформирована двумерная сетка из блоков размером $16 \times 16$ потоков. Использование скалярных вещественных параметров (`startx, starty, endx, endy`) предотвратило внутреннюю ошибку типизации кортежей в LLVM CUDA.

Сформированное фрактальное изображение сохранено в `images/mandelbrot_gpu.png`.

![Множество Мандельброта](images/mandelbrot_gpu.png)

### 3. Сравнение производительности
Для оценки эффективности параллелизации сопоставлены замеры времени расчета матрицы $2000 \times 2000$:
* **Базовая версия на чистом Python:** ~64.09 с (последовательная интерпретация в CPython);
* **Локальный Numba Parallel (CPU):** ~0.81 с (многопоточный расчет с обходом GIL);
* **NVIDIA GeForce MX230 (стенд методички):** ~0.15–0.25 с (массивный параллелизм на аппаратных ядрах CUDA).

## Ответы на вопросы для самоконтроля к защите

### 1. В чём ключевое отличие функций ядер GPU (`@cuda.jit`) от обычных функций Python с точки зрения оператора `return`?
Функции ядер (Kernel functions) исполняются асинхронно тысячами параллельных потоков на видеокарте. Они не имеют возвращаемого значения в CPU (`return None`). Все результаты работы ядра записываются напрямую по глобальным индексам в переданные массивы памяти GPU (VRAM).

### 2. Что такое Grid, Block и Thread в архитектуре NVIDIA CUDA и как задаётся конфигурация запуска ядра?
* **Thread (Поток):** наименьшая единица исполнения кода ядра над одним элементом данных.
* **Block (Блок):** группа потоков, выполняющихся на одном потоковом мультипроцессоре (SM), имеющих общую разделяемую память (Shared Memory) и механизмы барьерной синхронизации.
* **Grid (Сетка):** вся совокупность блоков, запущенных для выполнения одного ядра.
* **Конфигурация вызова:** задаётся в квадратных скобках перед круглыми скобками аргументов: `kernel[blocks_per_grid, threads_per_block](args...)`.

### 3. Каким образом функция `cuda.grid(1)` вычисляет глобальный индекс потока?
Она инкапсулирует вычисление абсолютного смещения потока в одномерном пространстве сетки по формуле:
$$\text{cuda.grid}(1) = \text{cuda.blockIdx.x} \times \text{cuda.blockDim.x} + \text{cuda.threadIdx.x}$$
где `blockIdx.x` — индекс текущего блока, `blockDim.x` — количество потоков в блоке, `threadIdx.x` — номер потока внутри своего блока.

### 4. Почему при запуске 1008 потоков на массив из 1000 элементов проверка `position >= shape[0]` обязательна?
Потоки с индексами $1000, 1001, \dots, 1007$ не имеют соответствующих ячеек в выделенном буфере. Без проверки `if position >= shape[0]: return` произойдёт либо ошибка нарушения прав доступа к памяти (`Access Violation`), либо искажение соседних строк матрицы при двумерной индексации.

### 5. Для чего применяется параметр `device=True` в декораторе `@cuda.jit`?
Он компилирует функцию в статус **Device-функции**. Такая функция может вызываться исключительно изнутри другого ядра GPU, исполняется на стороне видеокарты и, в отличие от ядра, **может возвращать значение через `return`**.

### 6. Почему в кернел `compute_all_points` нельзя передавать кортежи параметров?
Внутренний генератор типов Numba CUDA не имеет полноценной поддержки низкоуровневого маршалинга гетерогенных кортежей Python в C-структуры ядра. Попытка передачи `tuple` приводит к ошибке компиляции в LLVM. Для корректной работы параметры координат передаются отдельными вещественными числами (`float32` / `float64`).

### 7. За счёт чего GPU демонстрирует многократное ускорение на задаче Мандельброта?
Расчет множества Мандельброта относится к классу задач **Embarrassingly Parallel** (идеально распараллеливаемых): значение цвета каждого пикселя вычисляется абсолютно независимо от соседних точек. В то время как CPU имеет ограниченное число ядер с длинным конвейером, GPU содержит тысячи специализированных вычислительных ALU-ядер, рассчитывающих тысячи пикселей одновременно за каждый такт.
